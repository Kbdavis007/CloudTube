## Cloudflare build failure: bun lockfile version (fixed, v0.2.17)
- Symptom: CF Workers Build aborts at `bun install --frozen-lockfile` with
  "Unknown lockfile version ... at bun.lock:2:22" then "lockfile had changes, but
  lockfile is frozen". Cause: the committed `bun.lock` was `lockfileVersion: 2`,
  which the build image's bun 1.2.15 cannot parse, so it discards the lockfile and
  the frozen check then fails.
- Fix: regenerate with the SAME bun version the builder uses (1.2.15 -> emits
  `lockfileVersion: 1`) and commit. Verify by reproducing locally: download the
  exact bun from the GitHub release zip (`python3 -c "import zipfile..."`, no unzip
  binary needed), then `bun install --frozen-lockfile` must print "no changes".
- The build image's tool versions are in the CF build log header ("Detected the
  following tools from environment: bun@X, nodejs@Y") - match bun to that.

  channel record, and never appeared on the Channels page. Fix: extract
  `src/services/channelExpansion.ts` (dependency-injected `ChannelExpansionStore`

## Issue #8 — /privacy and /tos pages (PR #10)

- **Why:** Google's OAuth consent screen (branding) needs a privacy policy + TOS on a
  verified domain you own, as a *dedicated HTML page*, linked on the homepage, with a
  Limited Use disclosure. `https://support.google.com/cloud/answer/13806988`.
- **Gotcha discovered:** the Worker SPA fallback made `/privacy` and `/tos` return
  **200 with the app shell** (CloudTube sign-in page). A naive check that only looks at
  the status code would wrongly conclude the pages already existed. `/privacy.html`
  also returned the shell — `public/` files were never reachable because the built
  `dist/` had no such files. Always grep the *body* (`<title>`), not just the code.
- **Friendly URL mapping:** Cloudflare's `assets.html_handling` default is
  `auto-trailing-slash` (`/file` -> `/file.html`; `/file.html` -> 307 `/file`), so the
  extensionless paths work once the `.html` files are in `dist/`. Pinned it explicitly
  in `wrangler.jsonc`. Verified with `npx wrangler@latest dev` — `/privacy` 200,
  `/privacy.html` 307, `/` and `/nonexistent` still the SPA shell.
- **Dev parity:** Vite's dev middleware answers unknown HTML routes with the app shell,
  so `server.ts` serves the legal pages from `public/` *before* `vite.middlewares`
  (dev only). Shared allowlist `worker/legalPages.ts` (`resolveLegalPage`) — explicit
  map, not filesystem-derived, so a file dropped in `public/` is never served.
- **Placement:** pages are standalone HTML in `public/` (no JS, no sign-in) because the
  React app is gated behind Google sign-in and a reviewer could not see it otherwise.
- **Privacy policy accuracy rule:** it discloses the ONE server-side store — the
  Cloudflare **D1 `video_search_cache`** (public video metadata keyed by source+query,
  TTL hours, shared by all users) — instead of claiming the app stores nothing
  server-side. Also notes the CF API token passes *through* `/api/cloudflare/proxy` in
  transit. Check the code before claiming "no server storage".

  (from git author). Reviewer should confirm before submitting for verification.
