## Daily Vega catalogue refresh (workflow added, v0.2.22)
- `.github/workflows/refresh-vega-catalogue.yml`: daily 06:17 UTC + manual
  dispatch. Scrapes -> rebuilds -> bakes into `src/data/vegaCatalog.json` ->
  **cuts a release** (`release.mjs patch --push`) -> optional CF deploy hook ->
  stamps the changelog. It must cut a release, not push a bare data commit,
  because AGENTS.md says "every push is a release". Needs `fetch-depth: 0`
  (release.mjs uses `git describe` + tags).
- `scrapers/vega/scrape.sh` drives the Firecrawl CLI. **Firecrawl fetches
  server-side, so the runner's IP is irrelevant** (this is why it works where the
  CF Worker's egress was blocked by xvideos). Per-page: `firecrawl scrape "$url"
  -f markdown,links --max-age 0 -o pNN.json`. `--max-age 0` forces a fresh fetch
  (without it you get Firecrawl's cache). Output JSON has `markdown`/`metadata`/
  `links` - exactly what `vega_parse.py` expects.
- **`FIRECRAWL_API_KEY` repo secret is NOT set, and the agent cannot set it.**
  Both `GITHUB_TOKEN` and `Github_Super_Token` get **403 on
  `/actions/secrets/public-key`** ("Resource not accessible ..."), so `gh secret
  set` / the encryption API both fail: the tokens lack Actions-secrets write.
  The workflow therefore skips the scrape with a `::notice::` when the secret is
  missing, so the run stays green and self-explaining. **Owner action:** add the
  key under Settings -> Secrets and variables -> Actions. (The other required
  secret, `CF_DEPLOY_HOOK`, is optional.)
- Firecrawl CLI is `firecrawl-cli` on npm (`sudo npm install -g firecrawl-cli`,
  v1.28.0). Bare `npm i -g` fails without sudo in this sandbox.

## Replaced Firecrawl with curl (Firecrawl kept as fallback) — 2026-11-06
- **The GitHub Actions runner IP is NOT blocked by xvideos** (probed with a scratch
  workflow, since removed): page 1 and page 11 both returned 200 with 27 result
  cards, and the thumbnail CDN returned 200. This is the fact that unblocked the
  whole thing — the Cloudflare Worker IP *is* blocked (that's why Firecrawl was
  bought), but the runner is not.
- **We never needed Firecrawl's markdown.** `vega_parse.py` regex-parsed the
  markdown anyway. The raw HTML is richer: each result is a
  `div.thumb-block[id=video_<eid>]` with `data-eid`, `p.title a[href|title]`,
  `span.video-hd-mark` (quality), `span.duration`, `p.metadata span.name`
  (channel), `N Views`, `text-disabled` (ago), and `img[data-sfwthumb]`
  (resolved thumbnail). BeautifulSoup gets 100% of fields, same as Firecrawl.
- **`THUMBNUM` placeholder**: raw HTML leaves `THUMBNUM` in thumbnail URLs and in
  the `/video.<id>/THUMBNUM/<slug>` watch path; Firecrawl's JS resolved it to a
  frame number (e.g. `7`). Any frame 1–9 returns 200. Fixes: use `data-sfwthumb`
  when present, else swap `THUMBNUM->1`; and strip the frame segment from
  `pageUrl` (frame-less `/video.<id>/<slug>` is canonical, returns 200).
- **Dedupe must be by canonical URL, not id** (user requirement): the same video
  can appear under different ids. The build now appends to the existing catalogue
  and dedupes on `pageUrl` with the frame segment removed, so the transition run
  (old frame URLs vs new THUMBNUM URLs) doesn't duplicate. Carries older entries
  forward instead of replacing the catalogue.
- **Bloat**: raw HTML is ~91 KB/page (~1.4 MB/day) vs ~25 KB JSON. Gitignored
  `scrapers/vega/data/vega_pages/` and untracked the old dumps — pages are
  intermediates; only the built catalogue is committed.
- Result: 15 pages in ~11s via curl (vs ~70s + 15 credits via Firecrawl); no key,
  no rate limit. Verified end-to-end on the runner: all 13 workflow steps green,
  scrape used curl, released v0.2.32, live.
